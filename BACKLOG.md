**B-11 · Verify CORS on the four discovery endpoints**
PRD §8.6 assumes Greenhouse, Lever, Ashby and Workday send permissive CORS headers, so a Manifest V3 service worker can fetch them directly with `host_permissions` and no backend hop. This is tagged `[assumption]` and is unverified — the loop's sandbox refuses egress to all four hosts. One `curl -I` per host with an `Origin: chrome-extension://…` header from an ordinary network settles it. Blocks writing any adapter, because a refusal on a documented provider forces a proxy and changes the cost profile of the whole engine. **Dhwani can close this in about two minutes; the loop cannot close it at all.** Note from 2026-10-12: the same four requests now answer a second question. PRD §8.7 assumes the handle in a hosted board URL (`job-boards.greenhouse.io/{token}`, `jobs.lever.co/{site}`, `jobs.ashbyhq.com/{name}`, Workday's `{tenant}.{pod}/{site}`) is byte-identical to the handle the API path takes — which is what makes handle *harvesting* possible at all. No provider documents the equivalence, and the Greenhouse, Lever and Ashby docs all refused to open from the loop's sandbox. So each `curl` should use a handle lifted from a real board URL: if it returns that board's jobs, both assumptions close together. Note from 2026-10-13: PRD §9.5 adds a third thing worth reading off the same four responses — whether each provider's job objects carry a posting date at all, or only a mutable `updated_at`. Freshness caps at 3 of 5 points for any job whose only date is mutable, so the share of each board that caps is the difference between a working freshness term and a decorative one. Note from 2026-10-16: a fourth, free reading — the byte size of one response's `content` / description field, which is the input to B-17. **Note from 2026-10-19, replacing the fifth note:** the rate-limit reading no longer blocks anything. None of the three documented providers publishes a read limit for its public board endpoint (PRD §8.9), so B-18 was never waiting on a number that existed and is now specified without one. The headers are still worth capturing when the `curl` is run — an *undocumented* throttle would show up as `X-RateLimit-*`, `Retry-After` or a 429 under repetition, and finding one would tighten §8.9's back-off rule from a precaution into a measurement — but it is now a nice-to-have on a request being made for the other four reasons. Use `curl -i`, not `curl -I`: the body answers the handle, date and size questions.

## Done

**B-01 · Fit score has no warm-connection term** — specified 2026-09-29 in PRD §9. Connection enters at 20 of 100, displacing 5 each from role match, experience match, company and narrative — the terms that predict fit but not conversation, and in the case of role/experience were double-counting one signal. The weights before that change, kept here because PRD §9.1 no longer carries its own history (R-03): role 30 / eligibility 20 / experience 15 / company 10 / narrative 10 / location 5 / authorization 5 / freshness 5, with no connection term at all. Tiers are scored by **what the person can do today** (C3 replied-or-will-refer 20 / C2 saved alum or contact, no reply 14 / C1 named but unsaved 8 / C0 nobody 0), never by an inferred closeness score, with C2 decaying to C1 after 21 silent days. Two CI-blocking invariants bound the term: connection re-ranks the qualified set but cannot admit a job below the role-fit floor, and C3 is worth exactly as much as company+narrative+location+freshness combined while staying smaller than role+experience. Explanation must name the person — if Hoshi cannot name them, it cannot award the points, which puts Principle 2 on the score itself. Weights and tier spacing tagged `[assumption]`: no public dataset resolves outcomes by connection strength, and B-04 has since established that one user's analytics cannot retire the tag either (PRD §10.4). The decay rule turned out to have a measurement consequence as well as a scoring one — see PRD §10.5, added 2026-10-09. §9.4 extended 2026-10-10: C1 must print where the person came from, not only who they are. **Invariant 2 corrected 2026-10-11:** it read *C3 exceeds the block* for twelve days, and 20 does not exceed 20 — the test is `==`, the guaranteed property is that a C3 job cannot be *outscored* on the four soft terms, and the tie is broken by §7.2's existing connection-tier tiebreak. Do not re-word it back, and do not bump a weight to make the old sentence true: that breaks the sum to 100.

Promotion rules moved out of §8.1, which should not have been specifying a surface. Spawned B-15. Second tiebreak narrowed 2026-10-13 by B-07. **B-03 · Discovery engine** — specified 2026-09-28 in PRD §8. No code written; see B-11 before any is. **Extended 2026-10-12 with PRD §8.7**, which closes the hole §8.1 left open: a person gives a company *name* and every adapter takes a provider *handle*, with no documented name→handle lookup anywhere, so the watchlist rule did not actually produce a fetchable board. Handles come from three places only — harvested from the URL of a job page the user already opened (free: the §4 ATS fingerprint already parses that URL), pasted by the user as a careers URL, or nowhere, in which case the company stays on the list as **person-only**, seeding people and §9's connection term while contributing 0 jobs. The storage cost of §8.1's whole-board subscription is B-17, opened 2026-10-16.

**Extended 2026-10-17 with PRD §8.8, delisting.** The competitive finding is structural rather than about a feature: nothing notifies a crawler when a role closes, which is why expired postings linger on aggregators, while the ATS record is what the employer edits and so reflects status changes fastest ([JobsPipe](https://jobspipe.dev/blog/job-aggregator-sites), a seller of ATS feed data — tagged, though the mechanism is not in dispute). §8.1 already polls the ATS record, so Hoshi had the one closure signal an aggregator cannot buy and was discarding it, while §9.5's `> 10 days → 0` band was ageing listings out on a timer — the same guess the source calls guessing. The rule: **a job absent from a response with `complete === true` becomes `closed` (`closedAt`, `closedReason: 'delisted'`); a job absent from a response that is incomplete, truncated, rate-limited, schema-mismatched or errored closes nothing at all**, because that is a failure to observe and not an observation of absence — Principle 5 applied to a negative. A page-extracted job at a person-only company has no board to be absent from and stays `unknown`, so there are three listing states and never two. Closed jobs leave both job blocks of the brief and are never scored or re-ranked; `live` with freshness 0 is still live. **Delisting writes no `outcome` event** (§10.5) — a posting coming down says nothing about the user's application, and logging it as `rejected` would fabricate a result into an append-only store that cannot take it back. Do not re-propose inferring closure from age, from a 404 on the apply URL without a complete-board observation, or from a tombstone page's text: the first two are the guess this section replaced, and the third is a page read Principle 4 does not cover. Spawned B-18 (polling cadence, which delisting latency now depends on) and gave B-17 its first eviction candidate.

**B-04 · No answer to "why did my response rate change?"** — specified 2026-10-02 in PRD §10. The finding that shaped it: **a single user cannot A/B test the application funnel at all.** Detecting a 5%→15% move in cold response rate needs 141 applications per arm, and a seeker reaching one interview per ~40 applications never gets there in a season. So the metric set leans to the warm path, where §1's base rate is an order of magnitude higher and therefore needs an order of magnitude fewer events, and the headline metric is **person-attached rate** — a proportion of the user's own behaviour rather than the market's, so it moves the same week. Metrics split into counts (exact, no interval) and rates (estimates, always with a 95% Wilson interval). Honesty rules replace "do not claim causality without enough data": no percentage under n=10, intervals at the same type size as the number, no comparative language unless two intervals are disjoint, no unsourceable external benchmark, and insufficient-data states that give the shortfall as a computed number. B-04's assigned job of falsifying §9.1's connection weight is **conceded as impossible at single-user scale** and recorded as such in §10.4, with two weaker substitutes. Spawned B-13. **Extended 2026-10-09** with an eighth honesty rule and §10.5: none of the tier or person-attached metrics may be computed from current state, because §9.2's tier changes after the event and the resulting bias runs in the direction that confirms §9.1. Spawned B-16. **Extended 2026-10-16** with a ninth rule — see B-16. **Extended 2026-10-21** with the `outreach` and `reply` kinds, which is rule 8 applied to the one metric group that had been left out of it: §10.2's outreach counts and the reply rate are the thesis' own numerator, and with no event behind them they could only have been read off §4's outreach tracking — current state. By rule 8's own closing sentence they were therefore not shown at all. §10.2's grain changed with them: the denominator is **outreach threads**, not contacts, because one person messaged twice in a season is two threads and a contacts-based denominator is not a reply rate. No code written.

**B-07 · Freshness is specified but unused** — resolved 2026-10-13 as PRD **§9.5**, by wiring rather than cutting. Freshness keeps its 5 of 100 and scores exactly one thing: **how full the applicant pool already is.** The band edges are measured, not chosen — DHI Group, linking ~80M applications to ~10M postings, reports 41% of applications arriving inside 48 hours and 56% inside 96, against a mean single-position posting life of 9.8 days ([St. Louis Fed](https://www.stlouisfed.org/on-the-economy/2017/november/how-quickly-people-apply-jobs)) — giving ≤48h → 5, 48–96h → 3, 4–10 days → 1, >10 days → 0, with the 5/3/1/0 spacing tagged `[assumption]`. **Freshness explicitly does not score the user's odds**, because the evidence that it would is not usable: the "2–3x more interviews for applying inside 48 hours" figure is one unpublished survey by a vendor selling application speed, and "90% of candidates who got interviews applied in the first 24 hours" is pool composition rather than a rate — with 41% of all applications arriving inside 48 hours, that is §10.5's self-confirming measurement again. **The date problem is the substantive half.** Greenhouse's `updated_at` moves on an edit or a repost, Ashby publishes a real publish date, and a DOM-extracted page may have neither, so every job records `dateKind: 'posted' | 'updated' | 'none'`: `none` scores 0 and says so, `updated` caps at 3 and names the field in the score line, and two new CI-blocking invariants (§9.3's shape) enforce both. §7.2's freshness tiebreak is narrowed to raw timestamps within one `dateKind`, falling through to company order across kinds — otherwise the brief ranks by which ATS the company bought. Weights untouched, so §9.1 still sums to 100 and §9.3 invariant 2 stands (both rechecked). **Do not re-propose cutting freshness and redistributing the 5**: that branch is closed, and it would break invariant 2 in one direction or the other. The open follow-on belongs to B-11, which should now also record how many of each board's jobs carry only a mutable date. The `> 10 days → 0` band's closure overtones were corrected 2026-10-17 by §8.8: age scores the pool, delisting observes closure, and the two are not the same claim. One freshness question that looked open and is not, as of 2026-10-19: a daily poll does not corrupt the bands, because the date is the provider's rather than Hoshi's first sighting — see B-18.

**B-16 · Submission events need a fifth store, and it is append-only** — resolved 2026-10-16 inside PRD **§10.5**, which now carries the schema as well as the argument for it. Both of B-16's open questions are answered, and the answers went the opposite way to the way the question was posed.

- **Outcomes are rows in the same store, not a sibling.** One append-only **event log**, three kinds discriminated by `kind`: `submission` (written at `mayMarkApplied`, carrying `roleFit`, `totalScore`, `weightsVersion` and the person and tier *as at submit*), `outcome` (`response | screen | interview | rejected`, joined by `jobId`), and `brief` (the promoted set and the conversation rows as they rendered, which is what §10.4's behavioural test actually asks about). Rule 8's hazard is mutation, not heterogeneity — two stores sharing one write rule are one store with a discriminator, and the brief record means there were three kinds anyway.
- **Retention: nothing is ever deleted, and the arithmetic is why.** `chrome.storage.local` holds 10,485,760 bytes ([Chrome docs](https://developer.chrome.com/docs/extensions/mv2/reference/storage)); a heavy year — 300 submissions, two outcome events each, a brief every morning — serialises to ~400 KB, under 4% of it, so the log takes ~25 years to matter. The retention question was premised on unbounded growth being a problem and it is not one. **Do not re-propose a pruning, rollup or archival rule for this store.** The quota risk is real but it lives in the job store's `descriptionHtml` — opened as B-17.

Two rules fell out of the schema. **A job's stage is derived from the log and never stored beside it**, because a `status` field the user can flip readmits rule 8 through the UI. And **honesty rule 9**: a rate's denominator excludes submissions inside a 21-day maturation window (`[assumption]`, set equal to §9.2's decay clock so there is one clock and not two), because absence of an outcome event means *not yet* rather than *no* — rule 8's bias running the other direction, deflating instead of flattering. Narrowed B-13: the excluded count is a second computed number that component must render. A job's *listing* state is not an outcome and writes nothing here (§8.8, 2026-10-17). **The log holds five kinds as of 2026-10-21, not three** — `outreach` and `reply` were added for the reason this item established, that one write rule makes one store with a discriminator (see B-04). The retention answer survives them, rechecked rather than assumed: serialising a heavy year of all five kinds gives **387 KB, 3.78% of the 10,485,760-byte quota, ~26 years to fill**, against 332 KB / 3.24% / 31 years for three — so the PRD's "about 400 KB, under 4%, roughly 25 years" is now the closer figure rather than a stale one, and no sentence needed changing. **The pruning branch stays closed.** No code written.

**B-18 · Discovery has no polling cadence, and delisting depends on one** — resolved 2026-10-19 as PRD **§8.9**. Opened 2026-10-17 by §8.8, and filed as blocked on B-11's rate-limit headers. **It was not actually blocked, and finding that out is the run's result.** LOOP.md's 2026-10-16 rule says fetch the documented limit before designing around it; the documented limit does not exist. Greenhouse *"publishes no rate limit for its GET endpoints"*, Ashby *"publishes no rate limit for the public job posting endpoint"*, and Lever *"publishes no rate limit for reading postings"* — Lever's only published figure, 2 requests per second, governs application POSTs, a different endpoint ([JobsPipe source notes](https://jobspipe.dev/sources/lever.md) per provider, a seller of ATS feed data and therefore tagged where it advises; Workday documents no API at all). So B-11 could only ever have returned headers, not a published ceiling, and the item had been waiting on a number nobody publishes.

What the section says, with the absent number treated as a fact rather than as permission:

- **The ceiling is behaviour, not a rate.** On a 429 or 5xx a board backs off exponentially, and that poll closes nothing (§8.8's incomplete-response branch).
- **Volume was never the binding constraint.** One request per documented board plus `ceil(jobs / 20)` for Workday (§8.2): twelve boards including two 200-job Workday boards is 30 requests a poll — one every 48 minutes at a poll a day — and fifty boards polled *hourly* is 2,280 a day, 0.026 req/s. Computed in Python, not estimated.
- **The brief is what binds.** §7 renders once a morning, so an interval shorter than the brief's buys latency the user cannot see. **One poll per board per day, completing before the brief is composed**, plus an immediate poll when a handle is harvested or pasted (§8.7).
- **Freshness survives it.** §9.5's date is the provider's, not Hoshi's first sighting, so the interval adds no error to the bands — only delay before a job can appear, at worst one interval, leaving 24 of the top band's 48 hours.
- **A failed poll leaves a stale `live`, so it has to say so.** `BoardSource` records `lastCompleteAt`, and a job whose board has gone more than two intervals without a complete response returns to `unknown` rather than remaining `live`. This is the gap §8.8 opened by closing nothing on a failed poll: without it, an unreachable board asserts a listing state indefinitely.
