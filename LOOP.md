# Hoshi Loop — operating doc

Read this first, every run. It decides what today's run does.

Hoshi is Dhwani's Chrome extension (Manifest V3) for job search: it recognises job pages, extracts postings, fills applications without ever submitting them, and tracks the people worth talking to. She is a UX Research & Design master's student at UMSI targeting product design and UX research roles, and she needs visa sponsorship.

**The job of this loop is to make the PRD sharper every day, and to make Hoshi the best job-finding tool by the definition in PRD §5.**

1. **Read `claude/hoshi/PRD.md`.** This is the product. Everything answers to its §1 thesis.
2. **Read `claude/hoshi/BACKLOG.md`.** Never re-propose anything under Done or Rejected.

## What "improve the PRD" means

**It means sharper, not longer.**

- A run that deletes a vague paragraph and replaces it with a testable sentence is a good run.
- A run that adds a section nobody asked for is a bad run, even if the section is well written.
- Every factual claim needs a source link or an explicit `[assumption]` tag. Untagged assumptions are the failure mode that makes a spec feel authoritative when it is guessing.
- If two sections say the same thing, merge them.
- If a requirement cannot be tested, either make it testable or cut it.
- **A research finding that produces no requirement is dead weight.** Added 2026-10-10. The 10-04 cut established that §2's rows were the weakest part of the document precisely because none of them changed a requirement; the 10-10 run therefore stopped at the point where its finding produced one (PRD §9.4's provenance rule) rather than at the point where it had an interesting fact. Saturday's job is not "learn something about a competitor". It is "change something in this document because of what a competitor does".
- **The PRD asserts the current product, not its history.** Added 2026-10-11 after R-03 cut §9.1's "Was → Now → Why it moved" table. When a run changes a number or a rule, the new value goes in the PRD and the diff goes in that day's brief and the backlog entry — never into a column, a strikethrough or a parenthetical kept alongside the live value. A PRD that carries its own changelog grows by one line every time it is corrected, and Sunday ends up cutting the record of why Sunday cut things. Dated section headers and the `[assumption]` tags stay; they are current state, not history.
- **An example earns its lines when it is normative.** Added 2026-10-18, as the test that chose that day's cut over the larger one available. §8.3's adapter interface and §9.4's score lines look like illustrations and are not — they state requirements in the only form those requirements have, and cutting them would delete a rule. §7.4's rendered brief is the one block in the document where nothing in it can be failed, which makes it the first example a future cut should take and the last thing to mistake for a requirement. Ask of an example: could an implementation be wrong against it? If not, it is decoration, however good it looks — and decoration is cut before prose that carries a rule. *(The brief mock was duly cut on 2026-10-19 as R-08, the morning after it was spared, when §8.9 forced the ceiling. The test outlives it: apply it to the next candidate.)*

**Target length: under 400 lines.** If the PRD is over that, Sunday's cut is mandatory regardless of what else is queued.

## Hard constraints

- **Do not guess the Open Questions in PRD §6.** They are hers. Guessing produces a spec built on a foundation she never agreed to. Ask in the brief instead.
- **Do not weaken the six principles in PRD §3.** They are enforced by tests in the codebase. If a proposal requires breaking one, the proposal is wrong.
- **Do not redesign the UI.** The design system is Material 3 with Quicksand and Nunito Sans, fixed at a 360px side panel, with a four-destination bottom nav (Orbit, Jobs, People, Activity). Work within it.
- **Do not invent build status.** The codebase is not attached to these runs. Report what previous briefs and the PRD say is built; do not claim a test passed that you did not run.
- **Pushes work now — but this is still a spec loop until Dhwani says otherwise.** The old constraint here said `github.com/dhwanib-del/hoshi` was empty and pushes were refused for this org. That was tested on 2026-10-02 and is false: a commit to `master` went through ([88dbb01](https://github.com/dhwanib-del/hoshi/commit/88dbb01aca67ef84f6ae77bfc450a1d3d664f950)), and the repo now holds the four spec docs. What has *not* changed: the extension codebase is still not attached to these runs, so there is nothing to write code against. A run may commit and push **spec docs**. A run must not start writing extension code into this repo — whether the loop does that is B-14, and it is hers to decide. If a run produces code worth keeping, it still goes in the brief as a fenced block.
- **The loop's sandbox cannot reach non-allowlisted hosts.** Web search and fetch work; `curl` to an arbitrary API does not. If a claim needs a live request to verify, tag it `[assumption]`, say in the PRD that it is unverified, and put the verification step in the backlog for Dhwani. Do not quietly assert it.
- **WebFetch may or may not need Dhwani's approval, so try it before tagging.** Written 2026-10-04 after a fetch of an already-cited source timed out waiting for a permission prompt nobody was awake to answer, and amended 2026-10-10 after two fetches of new sources went through unattended on the first attempt. So: a run cannot *count* on reading a page end-to-end, but it must not assume it cannot either. Attempt the fetch; if it times out, plan around search results and pages already quoted in the PRD, and tag the claim rather than citing a link the run never opened. Note that web search in this sandbox returns titles and URLs without snippets, so search alone rarely grounds a claim — the fetch is usually the only way to get a quotable sentence. Amended 2026-10-19: the refusals are not evenly distributed, and in a way that is worth planning around. On both 10-12 and 10-19 the three provider docs (Greenhouse, Lever, Ashby) refused while third-party pages about those same APIs went through on the first attempt. So when a primary doc refuses twice across runs, stop re-attempting it every Monday — reach for a page that *quotes* it, cite that page with its interest disclosed, and tag what rests on the quotation.
- **Arithmetic in the PRD gets rechecked, not retyped.** Added 2026-10-09. Every number the document asserts about its own maths — the power calculations in §10.1, the Wilson intervals in §10.3, the weight sums and invariants in §9 — is reproducible from the script in the 2026-10-02 brief or from three lines of Python. A run that moves, quotes or adds one of those numbers runs the check first. The sandbox has Python; this costs seconds and it is the one class of claim the loop can verify by itself rather than tag. Amended 2026-10-11: this is not a formality. The 10-11 run rechecked §9's weights only because a cut moved them, and found that §9.3 invariant 2 had claimed `20 > 20` since 2026-09-29 — in a clause the PRD says should be CI-blocking. **A relational claim counts as arithmetic.** Recheck the inequality, not only the sum.
- **A share of the successes is not a rate, and a vendor's number about its own product category is not evidence.** Added 2026-10-13, after the freshness research turned up "90% of candidates who got interviews applied in the first 24 hours" — which, against the 41% of all applications that arrive inside 48 hours, is mostly the arrival distribution, and is the same self-confirming shape PRD §10.5 already describes. Before a run puts an outcome statistic in the PRD, it checks two things: what the denominator is (successes, or opportunities?), and who benefits if the number is true. A statistic published by a tool that sells the behaviour the statistic recommends gets the §1 HiringReach treatment — cite it, disclose the interest, tag it — or it stays out. Amended 2026-10-17: a third check, cheaper than both. **Would the requirement change if the number were half what it says?** The ghost-job statistics refused that day (R-06) failed this one — §8.8 acts on a board that stopped listing a job whether the market is 5% ghosts or 40%. A statistic that cannot move a requirement does not need to be adjudicated, only left out.
- **A platform limit is a measurable fact, so measure against it before designing around it.** Added 2026-10-16. B-16 carried a retention question for a week on the intuition that an append-only log grows without bound. It does: to about 400 KB a year, against a 10,485,760-byte `chrome.storage.local` quota — so the honest answer was *no retention rule*, and the week of carrying it was spent on a problem that does not exist. The same four lines of Python found the real one in the job store's `descriptionHtml`. When a constraint is a documented number (a quota, a rate limit, a page cap), fetch the number and run the arithmetic before specifying anything that manages it. Designing a mechanism for a limit nobody has measured is the storage-shaped version of an untagged assumption. **Amended 2026-10-19: a null result is a finding, and an absent limit is not permission.** B-18 was filed as blocked on reading the providers' rate limits, and none of the three documented providers publishes one — so the dependency could never have delivered what the item was waiting for, and two days were spent on that premise. When the documented number does not exist, say so in the PRD with the sourcing for its absence, then name the limit that *does* bind and design against that one instead; §8.9's binding constraints turned out to be the brief's once-a-morning cadence and the MV3 service worker's own ceilings, neither of which is a provider's business. The failure mode this prevents is the opposite of the 10-16 one: not designing a mechanism for an unmeasured limit, but helping yourself to an unbounded one because nobody wrote a number down.
- **A PRD section number is a stable identifier. Retire it, never renumber.** Added 2026-10-18, when the Sunday cut deleted §2 outright (R-07) and left the document reading §1 → §3. Those numbers are referenced from BACKLOG.md, from every brief and from roughly forty places inside the PRD, so closing a gap by renumbering §3–§10 is a bigger and more error-prone diff than the cut that opened it, and it silently falsifies the archive. A deleted number is gone for good: not reused by a later section, not renumbered around, and not marked with a placeholder line — an explanation of the gap is the self-history the 10-11 rule forbids. The record of what the number held lives in the backlog's R- entry and that day's brief.
