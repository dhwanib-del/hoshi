## What I found

None of the public posting endpoints in §8.2 returns a named person, and the shape of the absence is the point. Greenhouse's board-API job object has no person field at all ([Apify's field list for the official Job Board API](https://apify.com/usestring/greenhouse-jobs.md)). Ashby's `hiringTeam` and `author` **do** exist — on the *authenticated* job endpoints; the public posting endpoints return title, department, location, workplace and employment type, published date and `descriptionHtml`, and no person ([Truto](https://truto.one/integrations/detail/ashby.md)). Lever's `hiring_managers` and `followers` likewise show up only through an authenticated connection ([Apideck](https://www.apideck.com/integrations/lever/postings)).

So the recruiter route doesn't fail for lack of parsing. It fails because the person is on the employer's side of a login, and §8.6's entire permission argument — no backend hop, `host_permissions` only, public endpoints — is built on Hoshi never having one. That makes it a permanent refusal, which is worth more in the backlog than "nothing extracts it yet": the next run can't re-propose it by writing a better extractor.

Two caveats I'm keeping honest about. All three readings are tagged `[assumption]`: the provider docs refused the sandbox again, so these are third-party integration vendors rather than the primary source. They agree with each other, and a vendor cataloguing fields has no reason to omit one, which is why I treated the direction as sound. And the Greenhouse witness is incomplete in one specific way — that scraper doesn't fetch descriptions, so it can only tell us there's no *structured* person field. A recruiter's name sitting inside the description prose is the second route, and it's closed on principle anyway: there's no response key to record as its `path` (§8.4), so pulling a name out of text is the inference Principle 2 forbids.
