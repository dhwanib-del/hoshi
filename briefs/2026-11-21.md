**Two public datasets, counting different things, and only the wrong one is reachable.**

The Labor Department's LCA disclosure file is reachable and is three steps from a petition count. A row is an **application**, and `TOTAL_WORKER_POSITIONS` is *"Total number of foreign workers requested by the Employer"* — so rows and positions are different numbers, **2.415x apart** (478,508 positions on 198,149 applications, FY2026 through 31 March, computed). Its decision is a wage-and-conditions **certification**, not a visa, and **91.8% of processed applications are certified against 0.47% denied** (191,095 and 977 of 208,171, computed from [OFLC's own statistics](https://www.dol.gov/sites/dolgov/files/ETA/oflc/pdfs/LCA_Selected_Statistics_FY2026_Q2.pdf), the agency publishing the data). A value true of nearly every employer that files discriminates between no two employers, so the only informative quantity is volume — which is exactly the quantity the unit was wrong about.

**And the finding proper is the publisher contradicting its own file.** The public file carries **no employer identifier**: *"The following form items are not included in the public disclosure file because they contain Personally Identifiable Information (PII): Employer's Federal Employer Identification Number (FEIN)…"* ([record layout](https://www.dol.gov/sites/dolgov/files/ETA/oflc/pdfs/LCA_Record_Layout_FY2024_Q1.pdf)), leaving `EMPLOYER_NAME` — *"Legal business name of the employer submitting"* — as the only handle. Meanwhile the same agency's statistics are *"aggregated based on the unique FEIN submitted by the employer"* and warn that *"Multiple appearances of the same employer name may occur when associated with multiple FEINs."* The name is not the employer, by DOL's own statement, and the name is all it publishes. So **a company-level total is unconstructible from the public file** — not hard, unconstructible — and any tool printing one has made a corporate-structure claim nobody checked. That is also why the competitor's per-posting label can be wrong in the way users report without anyone being able to check it.

**Why none of this was caught for a day is the reusable half.** The figure **scores nothing**, and every invariant in this document guards something that scores, is stored, or is counted. So it sat outside all of them and was free to name its own unit. *Scores nothing* is not *claims nothing*, and the words that exempt a figure from the scoring rules are the same words that stop anyone auditing it. A unit is the part that goes wrong, because a unit lives in prose and nothing consumes it — so no test can fail on one.

**Left open deliberately, and it is a storage question now rather than a sourcing one.** The reachable file is a quarterly bulk download: 198,149 rows at an assumed 300–800 bytes is **59–159 MB against a 10,485,760-byte quota**, six to fifteen times the whole thing. An `EMPLOYER_NAME` → positions index would fit — assumed 30–60k distinct filer strings at 40–70 bytes is **1.2–4.2 MB, 11–40% of the quota** — but that competes directly with the ~3,600-job ceiling §8.4 bought on 11-16. Three routes, none of them the loop's to pick: an index you build and import, a figure you paste for one employer, or a backend under Q2. Until one exists the honest state is *not looked up* everywhere, which is what the code renders.
