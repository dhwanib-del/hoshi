**The cause is a discriminator carrying two facts.** §10.5 specified the arms on 10-30 as *scored and Hoshi's* against *unscored and hers* — true at the time, because the two coincided — and invariant (12), written four days later in §9, separated them by creating a job Hoshi fills and cannot score. **The tell for next time:** 11-17 found two populations under one name. This is the mirror — **one population with no name**, which is worse, because the row is well-formed and only in the wrong bucket, and in an append-only store it stays there. For each discriminated union, name the single fact the discriminator records, then ask whether that fact is available at the write site; where it bundles two, the one the code can compute wins. And the case that breaks a schema is usually created by this loop's own later invariant — a constraint written in §9 created a case in §10 and nothing re-read the schema.
